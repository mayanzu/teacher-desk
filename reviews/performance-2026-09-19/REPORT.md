# 教师工作台：性能专项 Review 与修改方案

审查日期：2026-09-19。代码基线：`1520bf4`（main）。本报告只审查与提出方案，没有修改业务代码，也没有提交或推送。

## 1. 结论与优先级

当前版本已经解决了“普通重复切 tab 必须重新请求”的主要问题：浏览器共享内存缓存、请求合并、首次同步读取缓存都已具备。继续优化的重点应转向 **首次登录、冷学期、保存后再访问、多用户同时操作、首次导出和大文件处理**。

当前的主要瓶颈是请求链和缓存边界，不是静态页面绘制。仅把所有数据更早拉取，可能把等待时间前移，同时增加教务系统压力；仅增加并发，则可能放大高峰时的超时。

本次记录 19 项发现：6 项 P1、12 项 P2、1 项 P3。其中 R17 为用户补充的历史学期导出等待案例，与 R01/R04/R08–R10 交叉关联，单独列为端到端验收项，并非把所有底层原因重复计算为独立缺陷。P1 表示优先处理的关键路径、容量或生命周期问题，不表示已经在生产发生事故；P2 表示可重现的局部开销或需要补全的性能机制；P3 为需进一步测量后决定投入的改进。

## 3. 本地证据与基线

环境：Windows x64，Node v22.20.0，AMD Ryzen 5 3600。请求实验使用每次 20 ms 的模拟延迟；操作系统计时调度会让实测高于理论值。下载使用随机二进制模拟低可压缩文件，每种大小运行 5 次，计时取中位数。

| 实验 | 结果 | 可得结论 |
|---|---|---|
| `JWXT_FETCH_CONCURRENCY=1` 调用真实 `getSchedule` | 20 次请求，峰值并发 **5**，91.70 ms | 配置无法限制课表内部并发 |
| 外层并发 3，运行三个课表任务 | 60 次请求，峰值并发 **15** | 外层任务限制不能约束底层请求 |
| 正常教学进度表单，首个表格返回有效行 | **3 次串行请求**，72.91 ms | 不是源码注释所说的“每班一次” |
| 空教学进度表单 | **7 次串行请求**，169.40 ms | 空结果会遍历全部五种表格候选 |
| 一班进度汇总后再读取该班表单 | 汇总 4 次，打开表单额外 **3 次** | 聚合和明细没有共用数据层缓存 |
| 浏览器命中新鲜课表缓存 | **0 次网络请求** | 当前 tab 缓存优化有效 |
| 保存进度后访问原已缓存的课表/任务/成绩列表 | 无关查询新增 **3 次网络请求** | 保存导致全局失效，收益丢失 |
| 预热首任务暂停后轮换会话，再恢复 | 4 个旧会话任务继续启动，旧结果写入 tasks 缓存 | 后台队列缺少会话代际保护 |

下载管线测量：

| 合成原文件 | JSON 大小 | gzip 大小 | Base64 + stringify | 异步 gzip | JSON 解析 + atob + 字节循环 + Blob |
|---|---:|---:|---:|---:|---:|
| 1 MiB | 1,398,176 B | 1,053,118 B | 2.92 ms | 34.82 ms | 19.49 ms |
| 8 MiB | 11,184,884 B | 8,424,257 B | 23.41 ms | 278.71 ms | 56.97 ms |

当前构建：JS 287.62 kB，构建器报告 gzip 88.95 kB；CSS 45.11 kB，gzip 9.30 kB。构建器 gzip 结果不等于服务器 level 4 实际传输字节。这个体积值得预算管理，但尚无证据说明它比教务请求链更重要。

## 4. 逐项发现与具体修改方案

### R01 · P1：必须在实际网络出口统一限制并发

**证据**：[server/jwxt/schedule.mjs:3](C:/Users/mzj/Desktop/code/课表/server/jwxt/schedule.mjs:3)、[server/jwxt/concurrency.mjs:30](C:/Users/mzj/Desktop/code/课表/server/jwxt/concurrency.mjs:30)、[server/session.mjs:53](C:/Users/mzj/Desktop/code/课表/server/session.mjs:53)、[server/index.mjs:229](C:/Users/mzj/Desktop/code/课表/server/index.mjs:229)。

`getSchedule` 硬编码每批五周的 `Promise.all`，不读取并发配置。其他模块的 `mapWithConcurrency` 各自管理自己的队列；服务端预热又套一层队列，多个浏览器请求同时执行时额度不会共享。已复现配置为 1 仍产生 5 并发；三个独立任务产生 15 并发。这不是测得生产峰值，而是证明缺少统一约束。

**修改方案**：把调度器放到 `JwxtSession.request` 的实际 fetch 周围，提供“同一会话限制 + 同一教务源全局限制 + 有限队列”；鉴权/当前用户操作优先于后台预取。额度应覆盖响应体读取，不能收到响应头就释放。嵌套业务函数只拆任务，不再重复占用同一个信号量，避免死锁。写请求按会话和业务对象串行处理，避免为性能并发提交。

**验收**：混合课表、进度、导出请求时，设每会话额度 1，真实 fetch 峰值必须为 1；多会话仍遵守全局上限；取消和异常均释放额度。具体默认数值在目标服务器及真实上游许可范围内小流量验证，不能承诺并发越高越快。

### R02 · P1：首次课表展示被整学期请求链阻塞

**证据**：[server/jwxt/schedule.mjs:7](C:/Users/mzj/Desktop/code/课表/server/jwxt/schedule.mjs:7)、[web/src/components/WeekSchedule.tsx:186](C:/Users/mzj/Desktop/code/课表/web/src/components/WeekSchedule.tsx:186)。

默认取 20 周，分四批；每一批必须等待最慢一周完成，最后统一返回 JSON。浏览器只有等完整结果才能渲染课表。即使当前周已完成，也无法先显示。任一周异常还会让本次整学期加载失败。

**修改方案**：首先验证上游是否存在可靠整学期接口；若没有，建立按周缓存，优先读取当前周及必要邻周，再后台补齐。API 需显式标记 `loadedWeeks`、`pendingWeeks` 和部分失败，避免把“未加载”误报成“没有课”。下一节课提示只使用已确认范围，补齐后更新。完整学期接口可保留供确实需要全量数据的操作使用。

批次循环也应改为统一调度器驱动的滚动队列，避免等待同批慢请求后才派发下一批。但这只能减少批次空闲，不能代替“先显示当前周”。

**验收**：把远端某一非当前周延迟设为 5 秒，当前周仍能先显示；保留跨周、单双周、补课及无课周的正确性。不能简单减少周数来制造提速。

### R03 · P1：教学进度汇总重复读取昂贵编辑数据

**证据**：[server/jwxt/progress.mjs:179](C:/Users/mzj/Desktop/code/课表/server/jwxt/progress.mjs:179)、[server/jwxt/progress.mjs:486](C:/Users/mzj/Desktop/code/课表/server/jwxt/progress.mjs:486)、[server/index.mjs:407](C:/Users/mzj/Desktop/code/课表/server/index.mjs:407)。

汇总直接调用 `getProgressClasses`，绕过路由上的 `progressClasses` 缓存。每班调用完整 `getProgressEntry`：表单、表格、学期周数至少三次请求。空表格会依次尝试五个表格 ID，达到七次。学期周数只依赖学期，却为每班重复请求。聚合完成后再次打开编辑明细还会重走这些路径；服务端明细没有共享缓存。

**成本模型**：若有 N 个班且首次表格均成功，汇总通常为 `1 + 3N` 次；六班为 19 次，不含鉴权。遇空表或候选表格不匹配会更多。当前汇总单个班级失败需要等其他班处理完成后一起返回。

**修改方案**：抽出会话隔离的数据访问层，复用班级列表、班级内容和学期周数。汇总只请求需要的只读字段，编辑时再获取必须保持最新的表单元数据；不要长期复用可能变化的隐藏字段/令牌。记录经验证的表格 ID，明确区分“合法空表”和“不匹配页面”；只在不匹配时回退。不能看到任意空提示就贸然停止，需要用实际页面 fixture 验证。

**验收**：同学期周数最多一次；已有明细构建汇总不重复回源；空表识别有独立测试；聚合正常、部分失败和 401 均保持语义。必须新增成功表单路径的请求预算测试，现有并发测试中有“表单解析失败立即结束”的样本，不代表成功路径成本。

### R04 · P1：后台工作没有完整绑定会话与页面生命周期

**证据**：[server/index.mjs:229](C:/Users/mzj/Desktop/code/课表/server/index.mjs:229)、[server/index.mjs:284](C:/Users/mzj/Desktop/code/课表/server/index.mjs:284)、[web/src/api.ts:172](C:/Users/mzj/Desktop/code/课表/web/src/api.ts:172)、[web/src/api.ts:194](C:/Users/mzj/Desktop/code/课表/web/src/api.ts:194)。

前端 cleanup 只设置 `stopped`，已经开始的 fetch 不会取消；服务端预热没有检查任务发出时 `ctx.session` 是否仍是原会话。`clearCache` 删除 inflight 能阻止已登记旧任务写缓存，但无法阻止后台队列在清理后继续启动新任务。退出/换账号时，这些后启动任务仍捕获旧 `session`，却使用同一个 `ctx` 的缓存空间，存在旧会话结果重新填入缓存的路径。已将当前源码中的 `cached` 和 `warmUp` 函数体原样提取、注入模拟数据加载器复现：暂停首个任务、轮换 ctx 会话并清空缓存、释放任务后，仍启动 4 个携带旧会话的后续任务，`tasks` 缓存写入旧会话标识。该实验验证函数级生命周期问题；没有操作真实账号。

预热在 API 路由处理前触发，包括已存在会话但尚未验证存活的请求。前后端预热同一个键通常会被服务器 inflight 合并，不能把两套预热直接等同为双倍请求；真正问题是无统一优先级、不同数据路径的重复工作、过期/取消后继续执行。

服务端还主动预热 `grades` 三张登记册，但目前“成绩录入”tab 只显示开发中，主界面的成绩导出使用另一套课程列表。这部分冷启动工作没有当前可见入口消费。

**修改方案**：每个 ctx 增加会话 generation；任务入队、出队和写缓存都校验 generation/会话身份。退出和切学期取消未启动预取；有多个前台消费者的共享请求按订阅计数决定是否中止。前后台共用优先队列；移除无 UI 消费者的数据集。预热失败可有受限重试，不能单次失败后被 WeakSet 永久视为已完成。

**验收**：让第一批任务阻塞，执行退出或会话轮换，再释放阻塞；不再启动旧会话任务，不写回旧数据，不占用新会话额度。切学期不继续批量拉取无用户关注的旧学期。保存失效时能取消或重新调度相关后台任务。

### R05 · P2：一次保存会使整个工作台重新变冷

**证据**：[web/src/api.ts:122](C:/Users/mzj/Desktop/code/课表/web/src/api.ts:122)、[server/index.mjs:214](C:/Users/mzj/Desktop/code/课表/server/index.mjs:214)、[server/index.mjs:427](C:/Users/mzj/Desktop/code/课表/server/index.mjs:427)。

前端在保存成功后 `clearApiCache()`；后端在 `saveProgressEntry` 返回后清空查询、导出和 inflight，未先确认上游业务状态成功。课表、学期、教学任务及成绩被一起清除。浏览器 generation 改变后，正在运行的预加载也会停止派发，但 App 的预加载 effect 不依赖 generation，不会因此自动重启。服务端 warmed 标记同样不会重置。

已复现保存后访问三个无关模块会新增三次浏览器请求；课表若也被后端清掉，则可能再触发 20 次上游请求。

**修改方案**：采用资源标签或结构化键定向失效：对应 `term + course + class` 的进度明细、学期汇总、相关 CSV/PDF；保留无关查询。确认业务成功后失效，失败不清空。成功保存可用服务器确认的数据更新已打开视图，再后台刷新摘要。不要把本地未提交草稿当作已保存结果共享。

**验收**：保存后课表/任务/成绩切换为 0 次无关请求；进度汇总与导出显示新数据；失败保存不破坏缓存；正在执行的旧汇总不能盖回新值。

### R06 · P2：后台刷新失败仍会让已显示内容消失

**证据**：[web/src/lib/queryCache.ts:21](C:/Users/mzj/Desktop/code/课表/web/src/lib/queryCache.ts:21)、[web/src/components/WeekSchedule.tsx:121](C:/Users/mzj/Desktop/code/课表/web/src/components/WeekSchedule.tsx:121)、[web/src/components/WeekSchedule.tsx:196](C:/Users/mzj/Desktop/code/课表/web/src/components/WeekSchedule.tsx:196)、[web/src/components/CourseGrades.tsx:159](C:/Users/mzj/Desktop/code/课表/web/src/components/CourseGrades.tsx:159)、[web/src/components/ProgressView.tsx:99](C:/Users/mzj/Desktop/code/课表/web/src/components/ProgressView.tsx:99)。

`peekQuery` 无条件返回旧值，适合先显示缓存，但没有提供缓存时间或过期状态。过期数据后台查询失败后，课表主动 `setData(null)`，其他列表通过 error 分支隐藏原内容。于是弱网下用户会先看到内容，随后被错误页替换。页面一直停留时，也没有订阅/定时机制保证数据在五分钟后更新；五分钟仅决定下一次查询是否发请求。

**修改方案**：统一查询 hook，区分 `initialLoading`、`refreshing`、`refreshError`、`updatedAt`；已有数据显示刷新警告并保留内容，401 则仍按登录失效处理。为不同数据设 freshness 和最大可展示年龄；超过上限要明确标记，不能无限静默展示。需要跨组件更新时增加查询订阅，以资源版本驱动，而非每个组件各自维护数据副本。

前后端缓存年龄应联动：服务端返回源数据生成时间/版本，前端不能把“读到服务器旧缓存”重新算成刚从教务读取。长期驻留页面可在恢复可见或相关操作后再验证，不必每条记录轮询。

### R07 · P1：缓存容量并未真正受到内存预算约束

**时间拆分模型**：

`点击到文件保存 = 登录验证 + PDF 生成 + 上游文件读取 + 可选文件名查询 + 服务端编码压缩 + 客户端传输/解码保存`

其中热缓存可以跳过生成、上游文件读取和文件名查询；后台请求竞争可能增加各项时间。当前系统没有统一应用请求队列，因此在新增计时之前，不应把观测到的等待全部称为“应用队列等待”。

#### 17.4 针对此体验的修改方案

1. **先补立即反馈**：点击后一个渲染周期内显示“正在生成 PDF…”，禁用同文件重复点击；接收后显示“正在准备保存…”，失败恢复按钮。没有服务端进度数据时不能伪造百分比或精确步骤。
2. **让文件名脱离关键路径**：复用已缓存的教师/成绩元数据；没有时使用可用的课程、班级文件名。确需查询时与生成并行、设短预算，不能在 PDF 下载完成后再阻塞一个完整超时。
3. **让当前操作优先**：历史学期切换后先加载当前 tab；其他模块闲时预取。导出时暂停尚未启动的低优先级预取，共用 R01 的底层调度与额度。单纯前端少开几个 Promise 不能约束后端内部的 20 周请求。
4. **复用完成的文件**：在字节预算内缓存 PDF；历史学期文件可考虑比当前学期更长的有效期，但必须允许成绩更正后的主动刷新、版本失效和账号隔离。不能假定历史成绩永远不变。区分会影响 PDF 内容的打印参数与纯下载名称，减少可避免的缓存键碎片，但标题若影响 PDF 内容必须保留在键内。
5. **按阶段决定后续优化**：生成本身占主导时，文件缓存或异步生成任务更重要；编码/传输占主导时再优化二进制路径/编码复用；不要把这类 10 秒等待都归为带宽问题。若导出确实经常长时间生成，可设计任务创建、状态查询、完成后下载，并继续保证幂等和会话隔离。

#### 17.5 必须补充的诊断与验收

| 对照场景 | 要记录什么 | 用来区分什么 |
|---|---|---|
| 切历史学期后立即首次导出 | 点击、请求发出、响应头、响应体完成、文件保存；各后端阶段；文件字节 | 冷生成与无反馈，定位这次约 10 秒 |
| 同文件完成后立刻再次导出 | 缓存命中、上游请求数、编码耗时 | 首次生成成本与热下载成本 |
| 预取完成后再导出另一份未生成文件 | 使用相同数据规模、交替测试并记录教务阶段 | 后台竞争；避免第二次已命中 PDF 缓存造成错误结论 |
| 5 分钟 TTL 后或清除测试环境对应文件缓存后再次导出 | 是否重新生成、是否额外鉴权 | 缓存期限与登录探测成本 |
| 文件已准备好，但姓名元数据延迟 10 秒 | API 完成时间 | 修复后不再被可选元数据拖住 10 秒 |
| 教务生成自身延迟 10 秒 | 按钮即时反馈、取消、任务去重 | 无法消除的上游耗时应被明确反馈，而非“点击没反应” |
| 当前与历史学期、相近人数/页数的班级 | 文件大小、生成时间、命中状态、后台请求数 | 不能只根据学期新旧判断原因 |

建议单独记录 `auth_ms`、`cache_hit`、`pdf_generate_ms`、`upstream_file_read_ms`、`filename_metadata_ms`、`encode_ms`、`response_bytes`，并用请求 ID 关联前端阶段。TTFB 只能说明响应头何时到达，不能代替总下载时长；后端 `finish` 也不能代替浏览器已经完成保存。

操作反馈目标可先定为基准环境点击后 **100 ms 内出现忙状态**；这是拟议验收目标，不是已测成绩。总下载时间应分别针对冷/热缓存、文件大小、上游延迟定义，不能承诺在教务生成本身耗时 10 秒时仍一秒完成。

### R18 · P2：点名册小文件导出仍会等整学期课表

**证据**：[server/index.mjs:547](C:/Users/mzj/Desktop/code/课表/server/index.mjs:547)、[server/jwxt/roster.mjs:237](C:/Users/mzj/Desktop/code/课表/server/jwxt/roster.mjs:237)。

报告接口并发拉取名单、课表、教学班列表和学期列表，然后等全部完成。教师姓名和编号可以从教学班的 `jsxm/jsdm` 获得，模板也优先采用这些字段；即使这些字段已完整，仍会读取课表并等待它完成。冷课表会产生 20 次按周请求。`.catch(() => ({}))` 只提供失败回退，不会缩短失败前的等待。

因此“点名册只有几十行，文件很小，为什么也要等很久”存在明确的代码解释：等待的是报表附属数据，而不是文件传输。点名册 CSV 路径只使用名单，不读取整学期课表，所以不能把两种下载格式的等待归为同一个原因。

**修改方案**：先复用名单与教学班数据；教师信息已足够时跳过课表。确实缺失时，读取缓存中的教师元数据或采用明确的缺失展示；若必须回源，使用针对教师信息的轻量查询及预算。学期名称优先复用已取得的学期字典。不要为了报表页眉硬依赖一整学期课程。

**验收**：教学班已经包含完整教师字段时，报告导出上游课表请求为 0；给课表请求注入 10 秒延迟不影响这种报告完成时间；教师字段缺失时回退可用且不误用其他教师信息。分别测试 CSV、XLS/HTML 报告，不能用较快的 CSV 成绩代替报告验收。

### R19 · P2：重试一次后，课表跨学期加载可能持续绕过缓存

**证据**：[web/src/components/WeekSchedule.tsx:92](C:/Users/mzj/Desktop/code/课表/web/src/components/WeekSchedule.tsx:92)、[web/src/components/WeekSchedule.tsx:106](C:/Users/mzj/Desktop/code/课表/web/src/components/WeekSchedule.tsx:106)、[web/src/components/WeekSchedule.tsx:200](C:/Users/mzj/Desktop/code/课表/web/src/components/WeekSchedule.tsx:200)、[web/src/App.tsx:230](C:/Users/mzj/Desktop/code/课表/web/src/App.tsx:230)。

课表用 `attempt > 0` 决定是否带 `refresh=1`。用户点击一次错误重试或空课表的重新加载后，attempt 不会在成功后归零。课表组件的 key 仅包含账号，在课表页面直接切换学期时保持同一组件实例，term 变化触发 effect，但 attempt 仍大于零。因此普通切学期也继续强制刷新，浏览器和服务端的新鲜缓存被绕过；切回刚看过的学期仍可能重新拉 20 周。

这是“有时缓存很快，出错重试过一次后又变慢”的条件性代码缺陷。切换到其他主 tab 会卸载课表，可能重置 attempt，因此现象并非每次都会持续。其他页面也存在 `attempt > 0` 写法，但 App 的 page+term key 通常会使它们跨学期重挂载，不能笼统宣称所有页面都有同样的持续问题。

**修改方案**：把强制刷新作为一次显式 query/refetch 操作，绑定具体缓存键；普通 effect 始终按缓存策略加载。若保留计数器，必须记录本次请求是否真正由新的刷新动作触发，不能只判断历史计数大于零。不要简单在 finally 中将 attempt 归零，从而让依赖它的 effect 额外再请求一次。

**验收**：A 学期请求失败 → 点击重试并成功 → 普通切换已缓存 B → 再回 A：只有重试那一次携带 refresh=1；普通切换为 0 次新鲜数据请求。连续主动点击刷新、快速切学期和乱序完成也要独立测试。

## 5. 建议的数据与请求架构

```text
用户交互 / 可见页面
  └─ 统一查询 hook：数据、更新时间、刷新状态、错误、订阅
       └─ 浏览器查询仓库：账号代际 + 学期 + 资源身份
            ├─ 新鲜命中：立即显示，无请求
            ├─ 过期可用：显示旧数据，受控更新
            └─ 无数据：当前页面优先，预取排在后面
                 └─ 服务端查询仓库：共享底层数据，定向失效，字节预算
                      └─ 上游统一调度：会话额度 + 全局额度 + 优先级 + 取消
                           └─ fetch / 读取响应体 / 校验 / 解析
```

建议先定义缓存契约，再实现细节：

| 资源 | 建议策略 | 失效/刷新 |
|---|---|---|
| 学期列表、教师基本信息 | 长 freshness，带来源时间 | 换账号、主动刷新、跨学期验证 |
| 当前周课表 | 前台高优先级，按周记录完整性 | 主动刷新/调课后更新，避免假空表 |
| 教学任务/教学班/课程成绩列表 | 登录后有限并发预取 | 按对应资源刷新，不互相清空 |
| 进度内容与汇总 | 共用只读底层缓存，摘要可派生 | 保存成功按班级和学期定向失效 |
| 编辑表单元数据 | 短有效期或进入编辑时验证 | 不与长期只读内容等同缓存 |
| 成绩明细/点名册 | 首次使用缓存，按需预取 | 数据变化或人工刷新 |
| 导出文件 | 按来源版本缓存，字节预算 | 对应数据保存后失效，不全站清除 |
| 草稿/周次/展开状态 | 与服务器快照分开 | 草稿确认规则保持；账号隔离 |

浏览器内存缓存足以解决同页 tab 切换。IndexedDB 用于刷新整个网页后恢复数据属于后续能力，需定义账号代际、最大陈旧时间、退出清理和多标签同步；它不是当前第一优先级。

## 8. 不建议现在做的改动

- 不直接把并发从 3 调到 10/20：先解决统一额度和优先级。
- 不在登录时下载所有历史学期、所有 PDF：这会扩大冷启动成本及内存。
- 不为了“零转圈”无限延长缓存，也不跳过鉴权和保存后的必要失效。
- 不把所有 tab 永久隐藏挂载：编辑表单、心跳与倒计时也会常驻运行。
- 不先上 Redis、集群或复杂 Service Worker：当前单实例内的请求复用与预算尚未完整，新增基础设施会增加失效和会话一致性成本。未来多实例部署再专门设计共享会话/缓存或粘性路由。
- 不把 Worker、虚拟列表、代码拆包当成必做项：先确认真实浏览器瓶颈。
